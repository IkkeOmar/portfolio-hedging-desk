# Contributing to portfolio-hedging-desk

Thanks for looking. This is a small, self-hosted portfolio-hedging desk: five
seats, an append-only journal, one veto, and four evaluation gates that a
hedge has to pass before anyone should believe it. It is MIT licensed and it
exists to be read, forked and extended.

You do not need to be a quant to contribute. Every number in this repository
is meant to be reproducible by a command that lives in the repository, and
every statistical claim is meant to be checked against a library you can
read. If you find a claim that is not reproducible, that is a bug worth
filing.

Read `docs/METHODOLOGY.md` before you change anything. It is the intellectual
core of the project and it explains *why* the code is shaped the way it is.
This file explains *how* to extend it.

## What this repository is not

Two things, stated up front because getting them wrong is how a hedging
repository ends up quoted as a trading system.

**There is no live trading support.** The only execution adapter is the paper
broker in `src/execution/paper.py`. It refuses to execute an intent that
does not carry a Risk signature, and it refuses to run in live mode unless
the `LIVE` environment flag is explicitly set — and nothing in this
repository, its scripts, its tests or its CI sets it. There is no broker
integration here. If you fork this and wire a real broker, you own that
decision and its consequences entirely. See `SECURITY.md`.

**The bundled market data is a synthetic test fixture, not evidence about
real markets.** It is generated by `src/data/synthetic.py`: a common market
factor with slow regime changes, volatility clustering, stress windows where
correlations spike toward one, per-asset betas that differ, and occasional
jumps. That is enough to exercise the machinery honestly, and not one more.
No claim about real markets is made anywhere in this repository. The fixture
exists so that "run the thing yourself" needs no broker key, no network and
no API key.

If you point the desk at real data, say so — in the config, in the report and
in whatever you write about the result.

## Setup

```bash
git clone <your-fork-url>
cd portfolio-hedging-desk
python -m pip install -r requirements.txt
```

`requirements.txt` is the complete "everything you need to run the tests"
file: numpy, pandas, scipy and PyYAML, plus yfinance and matplotlib, plus
the five cross-validation libraries — skfolio, purgedcv, statsmodels,
scikit-learn and cvxpy. The desk itself only needs the first four, because
the evaluation libraries are imported lazily inside the functions that use
them; the test suite exercises those functions, so it needs the rest. If you
prefer extras over a flat file, `pip install -e ".[dev,market-data]"`.

Check the install with the test suite:

```bash
python -m pytest tests/ -q
```

That should report 33 passing tests. If it does not, fix your environment
before you change any code — a broken baseline makes every later judgement
worthless.

## The two entry points

Both are plain scripts. No install, no daemon, no scheduler.

```bash
python scripts/run_desk.py
```

Runs one trading day end to end: Scan → Quant → Hedger → Judge (×3) → Risk →
Execution. It prints what each seat decided and writes the journal. It exits
zero. Useful flags: `--config`, `--journal`, `--date`, `--json`.

```bash
python scripts/backtest.py
```

Runs the walk-forward backtest over the whole history and then runs the four
gates on the result. It writes `reports/evaluation.json` and
`reports/evaluation.md`. **It exits non-zero when the gates do not all
pass** — that is the point of the gate stack, not a bug, and it is why you
should not wire it into a CI step as a pass/fail gate on the strategy. Flags:
`--config`, `--journal`, `--out`, `--horizon`, `--trials`.

`--trials` is an honesty flag. It records how many strategy variants you
actually tried, under `trials_declared` in the report payload, so that the
number is on the record rather than in your head. If you tuned anything,
count it.

One honest note, because this is the kind of thing that is easy to
overstate: `deflated_sharpe` in `src/evaluation/metrics.py` takes that count
and applies the correction for having picked the best of N, but
`scripts/backtest.py` does not currently call it — it only records the
number. Wiring the DSR into the backtest report is a genuinely useful first
contribution, and the function is already there.

Both entry points are also what CI runs, on every push and pull request,
on Python 3.11 and 3.12. The workflow lives in `.github/workflows/ci.yml`.

There is a third script worth knowing about:

```bash
python scripts/audit_claims.py
```

It mechanically checks that every file path mentioned in the markdown
actually exists, and screens every numeric claim in the docs against the
numbers the code actually produces. Run it before you open a PR that touches
documentation.

## The conventions a reviewer will check

These are not style preferences. Each one exists because its absence produced
a wrong number at some point, and several of those wrong numbers are written
up in `notes/KNOWN-TRAPS.md`.

### 1. No look-ahead

A decision made on day *t* may only use data from strictly before *t*.

The chokepoint is `Backtester._cutoff_panel` in `src/backtest.py`, which
returns `panel[panel.index < pd.Timestamp(date)]`. Every seat receives that
cut-off panel and **does no date filtering of its own**. The seats
deliberately cannot check the date, because only the caller knows what the
desk was allowed to see; a seat that filtered by date itself would eventually
be handed the future and would eventually use it.

The fill happens at the close of the *next* day, through the pending-order
mechanism in `src/backtest.py`. The loop has two steps: step 1 executes
*yesterday's* pending order at today's close, and step 2 then decides using
only data before today. So an intent decided on *t* becomes a fill on *t+1*.

The live desk is one step ahead of that, by design: `Desk.run_day` decides on
the given `date` using the panel strictly before it, and fills on that same
`date`. Both are look-ahead-free — the desk simply never uses a price it
could not have known — but they are not the same convention, and if you
change one you have to think about the other.

One trap worth knowing: `PaperBroker.submit` takes the `fill_date` you give
it and does **not** check that it is on or after the intent's date. It will
happily fill an intent at a price from before the decision. The
no-look-ahead property comes from the callers passing the right date, not
from the broker enforcing it. If you write a new caller, pass the date
deliberately.

The forward-outcome helpers in `src/backtest.py` are aligned the same way:
`forward_compound(t)` is the compounded return over *t+1 … t+H*, never
including *t*.

### 2. Every cost is charged

There is no "costs off" mode. `Costs` in `src/config.py` builds the fee,
slippage and spread per side, and `PaperBroker.submit` charges all three on
every fill. The backtest subtracts cumulative costs from the compounding
base, so the net curve compounds the way a real account does. A strategy that
only works at zero cost is not a strategy, it is a rounding error.

### 3. One seat can veto, and nothing trades without a signature

`RiskPolicy.evaluate` in `src/policy/risk.py` is the only place an
`OrderIntent` is created, and it signs it with `RiskPolicy.sign`. The paper
broker refuses an intent without a `risk_signature`:

```python
if not intent.risk_signature:
    raise LiveTradingRefused(
        f"intent {intent.intent_id} has no Risk signature; the execution adapter will not act on it"
    )
```

Every rejection is recorded with the reason. A system that publishes its
veto reasons is auditable; one that quietly does nothing is not. The
kill switch is a file on disk at `journal/risk.kill_switch` — it survives a
crash, a reboot, and a human who needs the desk stopped right now.

### 4. The journal is written before the outcome

Every seat writes its `Decision` row before the fill exists, so the record
cannot be edited by hindsight. `Decision` carries `information_cutoff` (the
latest market data the seat was allowed to see) and `input_snapshot_hash` (a
hash of the exact inputs). If two runs disagree on the same day, the hashes
differ and you can find out which input moved.

Rows are append-only JSON Lines, and `Journal.write_decision` is idempotent
on `idempotency_key`, so re-running a day produces the same journal rather
than a second copy of it.

### 5. Never hand-roll a statistic a maintained library already ships

This is the convention the whole test suite is built on. Each test compares
our computation against a *different* library or solver, so a bug in one
implementation cannot hide behind the same bug in the other.

| Statistic | Library |
|---|---|
| Deflated / Probabilistic Sharpe, expected-max Sharpe | skfolio |
| PBO via CSCV, purged walk-forward, effective number of trials, minimum track record length | purgedcv |
| Newey–West HAC standard errors | statsmodels |
| Spearman rank correlation | scipy |
| Covariance shrinkage (Ledoit–Wolf) | scikit-learn |
| Convex-solver cross-check of the one hand-derived formula | cvxpy |

The **only** formula this repository derives itself is the minimum-variance
hedge ratio `f* = -cov(r_p, r_h) / var(r_h)`, and it is cross-checked
against cvxpy in `tests/test_hedge_math.py`. If you add a metric, you add
the cross-check too.

### 6. Failures are loud

A missing key, a misspelled value, an unreachable data source, a broken
assumption: all of them raise. `ConfigError` names the key and the file. An
adapter that cannot reach its API raises rather than quietly substituting
something else. A seat that raises inside the backtest is recorded in
`seat_errors` and shown in the report — because a desk that fails quietly
looks exactly like a desk that has nothing to do.

### 7. Every number is reproducible by a command in this repository

If you put a number in the docs, there is a command that produces it. If you
change the code, the numbers in the docs change with it, and you update them
in the same PR. `scripts/audit_claims.py` checks the file paths exhaustively
and screens the numbers against what the code actually produces — a screen,
not a proof, so read its output rather than trusting a green result.

## Extension point 1 — adding a seat

### The seat contract

There is no base class and no registration decorator. A seat is a plain
class with a method that takes a cut-off panel and returns a small dataclass.
The five seats differ in shape, and that is deliberate — a common base class
would have to abstract over "what does this seat consume and produce", and
the answer differs per seat.

Here is the real interface of each, as it exists today:

| Seat | File | Constructor | Entry method | Returns |
|---|---|---|---|---|
| Quant | `src/policy/quant.py` | `QuantPolicy(benchmark, lookback_days=252, ma_days=200)` | `evaluate(cutoff_panel, date=None)` | `RegimeSnapshot` |
| Scan | `src/policy/scan.py` | `ScanPolicy(benchmark, max_candidates=5, min_weight=0.0)` | `scan(cutoff_panel, holdings, betas, idio_vols)` | `list[ScanCandidate]` |
| Hedger | `src/policy/hedger.py` | `HedgePolicy(benchmark, hedge_instrument, lookback_days=252, shrinkage_k=60.0, horizon_days=21)` | `estimate_all(cutoff_panel, symbols)` and `build_proposal(date, cutoff_panel, candidates, equity, costs, dial, max_hedge_pct_equity)` | `dict[str, HedgeEstimate]` and `HedgeProposal \| None` |
| Judge | `src/policy/judge.py` | `RuleBasedJudge(model_name="rule-based-v1", min_vol_reduction_pct=0.5, min_reward_to_risk=1.0, max_cost_bps=50.0)` | `judge(proposal, context, run=0)` | `Verdict` |
| Risk | `src/policy/risk.py` | `RiskPolicy(max_gross_hedge_pct=1.0, risk_per_trade_pct=0.02, min_reward_to_risk=1.5, max_legs=5, journal_root="journal", require_judge_agreement=True, min_judge_agreement=0.67)` | `evaluate(date, proposals, judge_summary, equity, costs, existing_gross_hedge_pct=0.0, open_legs=0)` | `RiskDecision` |

The Judge is the one seat with a formal protocol, `src/policy/judge.py`:

```python
class Judge(Protocol):
    """Interface every judge implements."""

    model_name: str

    def judge(self, proposal, context: dict[str, Any], run: int) -> Verdict:
        ...
```

That protocol is the pattern to copy if you are adding a *judge variant*. For
a genuinely new seat, follow the Quant or Scan shape.

### A worked example

Here is a complete sixth seat — a Concentration seat that flags holdings
which are too large a share of the portfolio to hedge meaningfully. It is
advisory: it cannot veto and it does not size anything, because only the
Risk seat does that.

Create a new module in the policy package. The file to create is:

```
src/policy/concentration.py
```

Its contents:

```python
"""The Concentration seat: is one holding doing all the work?

A hedge sized against a portfolio where one stock is 70% of the value is a
hedge against a bet on that stock. This seat is a screen, in the same
spirit as the Scan seat: it reports each holding's share of portfolio
value and flags the ones above a concentration limit.

It is deliberately advisory. It does not veto, it does not size, and it
does not touch the journal's decision flow: it returns a list of findings
that the desk records as a diagnostic. The Risk seat remains the only veto
and the only signature.

Look-ahead discipline
----------------------
``assess`` takes a cut-off panel and does no date filtering of its own.
"""

from __future__ import annotations

from dataclasses import dataclass, field
from typing import Any

import numpy as np
import pandas as pd


@dataclass
class ConcentrationFinding:
    """One holding that is too large a share of the portfolio."""

    symbol: str
    market_value: float
    weight: float
    limit: float
    detail: dict[str, Any] = field(default_factory=dict)


class ConcentrationPolicy:
    """Flags holdings that exceed a maximum share of portfolio value."""

    def __init__(self, max_weight: float = 0.25):
        self.max_weight = float(max_weight)

    def assess(self, cutoff_panel: pd.DataFrame, holdings) -> list[ConcentrationFinding]:
        """Return one finding per holding above the concentration limit.

        ``cutoff_panel`` must contain only prices from before the decision
        date.
        """
        if cutoff_panel.empty:
            raise ValueError("cut-off panel is empty")

        last = cutoff_panel.ffill().iloc[-1]
        values: dict[str, float] = {}
        for h in holdings:
            price = last.get(h.symbol, np.nan)
            values[h.symbol] = float(h.shares) * float(price) if np.isfinite(price) else 0.0

        total_value = sum(v for v in values.values() if np.isfinite(v) and v > 0)
        if total_value <= 0:
            return []

        findings: list[ConcentrationFinding] = []
        for h in holdings:
            value = values.get(h.symbol, 0.0)
            if not np.isfinite(value) or value <= 0:
                continue
            weight = value / total_value
            if weight > self.max_weight:
                findings.append(
                    ConcentrationFinding(
                        symbol=h.symbol,
                        market_value=float(value),
                        weight=float(weight),
                        limit=float(self.max_weight),
                    )
                )
        findings.sort(key=lambda f: (-f.weight, f.symbol))
        return findings
```

Note the two details that mirror the existing seats: the cut-off panel is
used as-is (no date filtering), and the output is sorted so the ordering is
deterministic across runs.

### What a new seat may and may not do

May: read the cut-off panel, read the holdings, write a `Decision` row, and
contribute a diagnostic to the report.

May not: create an `OrderIntent`, sign anything, or produce a fill. That is
the Risk seat's job and only the Risk seat's job. If your seat needs to stop
a trade, it has to raise a concern that the Risk seat's `evaluate` reads —
not raise it itself.

## Extension point 2 — adding a data source

### The adapter contract

Every adapter returns the same thing. This is stated at the top of
`src/data/__init__.py`:

```
index: DatetimeIndex (trading days, ascending)
columns: symbol -> close price (float)
```

Two rules, from the same docstring:

- Adapters never fill forward a price they do not have. A missing day is a
  missing day.
- A symbol with no history raises. We do not silently substitute.

The dispatcher is `load_panel` in `src/data/__init__.py`:

```python
def load_panel(source: str = "synthetic", symbols=None, start=None, end=None, seed: int = 20261024, path=None):
```

and the registry of valid names is:

```python
def available_sources() -> tuple[str, ...]:
    return ("synthetic", "yahoo", "csv")
```

The config side is `DataConfig` in `src/config.py`:

```python
@dataclass(frozen=True)
class DataConfig:
    """Where prices come from."""

    source: str = "synthetic"
    seed: int = 20261024

    VALID_SOURCES = ("synthetic", "yahoo", "csv")

    def __post_init__(self) -> None:
        if self.source not in self.VALID_SOURCES:
            raise ConfigError(
                f"data.source must be one of {self.VALID_SOURCES}, got {self.source!r}"
            )
```

So the `source` config key selects the adapter, and the list of valid
sources is duplicated in two places on purpose — `DataConfig.VALID_SOURCES`
for config validation, `available_sources()` for the dispatcher. **You must
update both.**

### The deterministic-synthetic behaviour

The synthetic source is the offline default and the reason this repository
runs with no network and no API key. It is deterministic: the same `seed`
produces the same market, every time, on every machine. `synthetic_panel`
takes `seed: int = 20261024` and drives `numpy.random.default_rng(seed)`,
and the per-symbol parameters live in the `_PARAMS` table at the top of
`src/data/synthetic.py`, with `DEFAULT_SYMBOLS` listing the default
universe.

The important subtlety, and it is the honest one: **there is no silent
fallback to synthetic.** If you configure `source: yahoo` and the API is
unreachable, the desk raises — it does not quietly fall back to the fake
market and keep running. Same for a CSV with a missing column (`KeyError`)
or a missing file (`FileNotFoundError`). A desk that silently swaps its data
source under you produces numbers that mean nothing, and this one is
supposed to produce numbers that mean something.

The practical consequence for you: when you add a source, decide explicitly
whether it fails loudly or falls back, and write down which you chose. The
repo's existing answer is *fail loudly*.

### Adding a CSV source

The CSV adapter already exists: `src/data/csv_source.py`, with
`csv_panel(path, symbols=None, start=None, end=None)`. It expects a first
column of dates and one column per symbol:

```csv
date,AAPL,MSFT
2020-01-02,125.06,160.37
```

This works out of the box. `DataConfig` carries a `path`, `Desk.load_panel`
and `scripts/backtest.py` both pass it to `load_panel`, and the config
validator refuses `source: csv` with no path — loudly, at load time, rather
than at the first read:

```yaml
data:
  # "synthetic" = bundled deterministic dataset, no network needed.
  # "yahoo"     = live-ish end-of-day prices via yfinance.
  # "csv"       = your own price file. Needs `path` below, and the file's
  #               first column must be a date.
  source: synthetic
  seed: 20261024
  # path: examples/prices_sample.csv
```

**It used to be broken, and the shape of the fix is worth knowing.** The CSV
adapter (`src/data/csv_source.py`) and `load_panel`'s `path` argument both
existed, and `DataConfig` advertised `csv` in `VALID_SOURCES` — but
`DataConfig` had no `path` field, so a config file could not select it and
the option raised no matter what you put in the YAML. An option the
configuration accepts and the code cannot honour is worse than one it
rejects, so if you add a source, wire the path all the way through in the
same change.

### Adding a brand-new API source

Say you want a source called `stooq`.

**1. A new module in `src/data/`** — a file named `stooq`. Copy the
shape of `src/data/yahoo.py`, which is the model to follow for a network
source:
retry with backoff, an optional parquet cache, and a loud error when a
symbol cannot be fetched.

```python
"""Adapter skeleton for a new price API.

Copy this file, rename it, and replace the body of ``stooq_panel``. The
contract every adapter must satisfy is in ``src/data/__init__.py``:

    index:   DatetimeIndex, trading days, ascending
    columns: one column per symbol, the close price (float)

Two rules, from the module docstring of the package:

* Adapters never fill forward a price they do not have. A missing day is a
  missing day.
* A symbol with no history raises. We do not silently substitute.

The synthetic source is the deterministic fallback: if this adapter cannot
reach its API, the desk does not quietly switch to fake prices, it raises
and the operator decides.
"""

from __future__ import annotations

import pandas as pd


def stooq_panel(symbols=None, start=None, end=None) -> pd.DataFrame:
    """Fetch daily closes for ``symbols`` and return a wide DataFrame."""
    if isinstance(symbols, str):
        symbols = [symbols]
    if not symbols:
        raise ValueError("stooq_panel needs at least one symbol")

    frames = {}
    for symbol in symbols:
        # ... your API call here ...
        series = pd.Series(dtype=float)  # index=DatetimeIndex, values=closes
        frames[symbol] = series

    panel = pd.DataFrame(frames).sort_index()
    panel.index.name = "Date"
    return panel
```

**2. `src/data/__init__.py`** — register it in both places:

```python
def available_sources() -> tuple[str, ...]:
    return ("synthetic", "yahoo", "csv", "stooq")
```

and add a branch to `load_panel`, before the final `raise`:

```python
    if source == "stooq":
        from .stooq import stooq_panel

        return stooq_panel(symbols=symbols, start=start, end=end)
```

**3. `src/config.py`** — add the name to the valid set:


**4. `examples/holdings.example.yaml`** — mention it in the comment above

**5. `tests/`** — a test that the adapter returns a panel with the right

## Extension point 3 — adding a metric or a gate

### The gate result shape

`GateResult` in `src/evaluation/gates.py`:

```python
@dataclass
class GateResult:
    """One gate's verdict."""

    name: str
    passed: bool
    headline: str
    metrics: dict[str, Any] = field(default_factory=dict)
    notes: list[str] = field(default_factory=list)

    def to_dict(self) -> dict[str, Any]:
        return {
            "name": self.name,
            "passed": self.passed,
            "headline": self.headline,
            "metrics": self.metrics,
            "notes": self.notes,
        }
```

`name` is the gate's identifier and it shows up in the report and in the
`short_circuited_at` field of `reports/evaluation.json`. `headline` is the
one-line result a human reads. `metrics` holds the numbers, and they are
rendered as a table in the Markdown report without any extra work.
`notes` holds the sentences that explain the verdict. Every gate that
reports a number also says where it came from — gate 1, for instance, sets
`"source": "Healy and Lo (2010), condition (B) and equation (7)"`.

### How the gates short-circuit

`run_gates` in `src/evaluation/gates.py`:

```python
def run_gates(
    r_squared: float,
    dial: np.ndarray,
    forward_vol: np.ndarray,
    hedged_returns: pd.Series,
    unhedged_returns: pd.Series,
    regimes: pd.Series | None = None,
    walkforward_sharpes: list[float] | None = None,
    total_cost: float = 0.0,
    hedge_instrument: str = "the hedge instrument",
) -> tuple[list[GateResult], bool]:
    """Run the four gates in order and stop at the first failure.

    Returns the list of gate results (which may be short) and an overall
    boolean. A report is written either way; see ``report.py``.
    """
```

The short-circuit is explicit and it is deliberate:

```python
    g1 = hedgeability_gate(r_squared, hedge_instrument=hedge_instrument)
    results.append(g1)
    if not g1.passed:
        return results, False

    g2 = regime_information_gate(dial, forward_vol)
    results.append(g2)
    if not g2.passed:
        return results, False
```

A hedge that fails gate 1 does not need to be tested on gate 3, and
pretending otherwise manufactures evidence. The list of results that comes
back may be short; the report says which gate it stopped at.

The thresholds are named constants at the top of the file, so every
judgement call is visible in one place:

```python
MIN_R_SQUARED = 0.25
MIN_VOL_IC = 0.02
MIN_VOL_IC_TSTAT = 1.96
MIN_SHARPE_IMPROVEMENT = 0.0
MIN_REGIME_PASS_FRACTION = 0.5
MIN_WALKFORWARD_PASS_FRACTION = 0.7
```

### Adding a metric that cross-validates against an independent library

`src/evaluation/metrics.py` holds the statistics. The conventions, from the
module docstring:

- `periods_per_year` defaults to 252.
- `risk_free` arguments are **per period**, never annual.
- Sharpe-style ratios use the *arithmetic mean* of excess returns, never
  CAGR. Dividing CAGR by volatility and calling the result a Sharpe ratio is
  a mislabelled statistic, and it is the single most common error in retail
  backtests. `tests/test_metrics.py` has a test that exists solely to keep
  the two from drifting together.

Here is a complete worked example: an expected-shortfall (CVaR) metric
computed via skfolio rather than by hand.

Add to `src/evaluation/metrics.py`:

```python
# ----------------------------------------------------------------- tail risk
def expected_shortfall(returns: pd.Series, beta: float = 0.95) -> float:
    """Expected Shortfall (CVaR) at level ``beta``, as a NEGATIVE fraction.

    The average loss in the worst ``1 - beta`` tail, so a negative number
    like -0.04 means "on the worst 5% of days, the portfolio lost 4% on
    average". Reported as a negative fraction, the same sign convention as
    ``max_drawdown``.

    Computed via skfolio's ``cvar`` rather than by hand, so the tail
    convention matches the reference implementation.
    """
    from skfolio.measures import cvar

    clean = returns.dropna()
    if len(clean) < 30:
        return float("nan")
    return float(-cvar(clean.to_numpy(dtype=float), beta=beta))
```

Then add the cross-validation test. The first test is the important one:
it compares our wrapper against the library called directly, so a bug in
ours cannot hide behind a bug in our understanding of the library.

```python
def test_expected_shortfall_matches_skfolio():
    """Our wrapper must reproduce skfolio's CVaR exactly."""
    from skfolio.measures import cvar

    rng = np.random.default_rng(7)
    r = pd.Series(rng.standard_normal(1000) * 0.01)
    assert expected_shortfall(r, beta=0.95) == pytest.approx(
        -float(cvar(r.to_numpy(dtype=float), beta=0.95)), rel=1e-12
    )
```

A second test pins the sign convention and the relationship to the tail:

```python
def test_expected_shortfall_is_negative_and_worse_than_the_mean():
    """A tail loss is negative, and worse than the average day."""
    rng = np.random.default_rng(8)
    r = pd.Series(rng.standard_normal(500) * 0.01)
    es = expected_shortfall(r, beta=0.95)
    assert es < 0.0
    assert es < float(r.mean())
    # The tail is an AVERAGE, so it is less extreme than the single worst day.
    assert es >= float(r.min())
```

If the metric is going to be used by a gate, export it from
`src/evaluation/__init__.py` as well — that file re-exports the whole
public surface of both `gates.py` and `metrics.py`, and its `__all__` list
has to match.

### Adding a gate

Say you want a fifth gate that checks the hedge actually controlled the
drawdown.

Add to `src/evaluation/gates.py`, above the runner:

```python
# ------------------------------------------------------------------- gate 5
def drawdown_control_gate(
    hedged_returns: pd.Series,
    unhedged_returns: pd.Series,
) -> GateResult:
    """Did the hedge control the drawdown?

    A hedge that lowers volatility but leaves the worst peak-to-trough
    loss untouched has not done the job a hedge is for.
    """
    hedged_dd = max_drawdown(hedged_returns)
    unhedged_dd = max_drawdown(unhedged_returns)

    passed = bool(
        np.isfinite(hedged_dd)
        and np.isfinite(unhedged_dd)
        and hedged_dd >= unhedged_dd
    )

    notes: list[str] = []
    if np.isfinite(hedged_dd) and np.isfinite(unhedged_dd):
        notes.append(
            f"max drawdown {unhedged_dd:.1%} unhedged -> {hedged_dd:.1%} hedged."
        )
        if not passed:
            notes.append("the hedged portfolio's worst drawdown is deeper than the unhedged one.")

    return GateResult(
        "drawdown_control",
        passed,
        f"maxDD {hedged_dd:.1%} hedged vs {unhedged_dd:.1%} unhedged",
        {
            "hedged_max_drawdown": float(hedged_dd),
            "unhedged_max_drawdown": float(unhedged_dd),
        },
        notes,
    )
```

Then add it to `run_gates`, in the position you want it to run. Position
matters, because the stack short-circuits: put it after the existing four if
you want it to be a final check, or before them if it is a precondition.

```python
    g4 = stability_gate(
        hedged_returns,
        unhedged_returns,
        regimes=regimes,
        walkforward_sharpes=walkforward_sharpes,
    )
    results.append(g4)
    if not g4.passed:
        return results, False

    g5 = drawdown_control_gate(hedged_returns, unhedged_returns)
    results.append(g5)
    return results, bool(g5.passed)
```

Export it from `src/evaluation/__init__.py`:

```python
from .gates import (
    GateResult,
    run_gates,
    hedgeability_gate,
    regime_information_gate,
    compensation_gate,
    stability_gate,
    drawdown_control_gate,
)
```

and add `"drawdown_control_gate"` to that file's `__all__`.

The report needs no changes: `src/report.py` renders whatever gates it is
given.

Finally, test the gate itself. Two tests, one for each direction:

```python
def test_drawdown_control_gate_passes_when_the_hedge_cuts_the_drawdown():
    rng = np.random.default_rng(1)
    idx = pd.bdate_range("2020-01-01", periods=400)
    unhedged = pd.Series(rng.standard_normal(400) * 0.01, index=idx)
    hedged = pd.Series(rng.standard_normal(400) * 0.003, index=idx)
    gate = drawdown_control_gate(hedged, unhedged)
    assert gate.passed
    assert gate.name == "drawdown_control"
    assert "hedged_max_drawdown" in gate.metrics


def test_drawdown_control_gate_fails_when_the_hedge_deepens_the_drawdown():
    rng = np.random.default_rng(2)
    idx = pd.bdate_range("2020-01-01", periods=400)
    unhedged = pd.Series(rng.standard_normal(400) * 0.003, index=idx)
    hedged = pd.Series(rng.standard_normal(400) * 0.010, index=idx)
    gate = drawdown_control_gate(hedged, unhedged)
    assert not gate.passed
```

### A word on the gates themselves

The four existing gates are not the usual information / cost / compounding /
stability stack, and that is not an oversight. A perfect hedge has **zero
forward-return correlation** by construction, so a return-prediction gate
would reject the best possible hedge and pass a useless one. The full
argument, with the citation, is in `docs/METHODOLOGY.md` and in the module
docstring of `src/evaluation/gates.py`.

If you add a gate, ask what question a hedge can actually answer. A gate
that a hedge structurally cannot pass is not a strict gate; it is a bug.

## Extension point 4 — changing the hedge instrument or the risk limits

Everything the desk is allowed to act on lives in one YAML file:
`examples/holdings.example.yaml`. There are five sections.

### The config keys

```yaml
portfolio:
  account_id: example
  base_currency: USD
  benchmark: SPY          # the market the hedge is measured against
  holdings:
    - symbol: AAPL
      shares: 100
    - symbol: MSFT
      shares: 60
    - symbol: NVDA
      shares: 40

hedging:
  # Instrument used to neutralise risk. One symbol, on purpose: complexity here
  # buys you nothing you can explain.
  hedge_instrument: SPY
  # Trailing window used to estimate how each holding moves with the market.
  # 252 trading days is one year.
  lookback_days: 252
  # Confidence weight for shrinking an estimated beta toward zero. Bigger
  # number = more shrinkage = more conservative hedge. See docs/METHODOLOGY.md.
  shrinkage_k: 60
  # Maximum share of portfolio value we are allowed to put into hedge legs.
  max_hedge_pct_equity: 0.60
  # How often to re-measure and re-trade.
  rebalance: monthly      # daily | weekly | monthly

risk:
  # The Risk seat refuses any order that breaks these. It has the final word.
  max_gross_hedge_pct: 1.0
  risk_per_trade_pct: 0.02     # 2% of equity per hedge leg
  min_reward_to_risk: 1.5      # do not take a hedge that costs more than it saves
  max_legs: 5

costs:
  # Honest numbers. If your broker is more expensive, raise these and watch
  # the edge shrink. That is the point of modelling them.
  fee_bps_per_side: 2.0
  slippage_bps_per_side: 1.0
  spread_bps_per_side: 0.5

data:
  # "synthetic" = bundled deterministic dataset, no network needed.
  # "yahoo"     = live-ish end-of-day prices via yfinance.
  source: synthetic
  seed: 20261024
```

The dataclasses behind them are in `src/config.py`: `Portfolio`, `Holding`,
`HedgingParams`, `RiskLimits`, `Costs`, `DataConfig`, and the `DeskConfig`
that holds them all. `DeskConfig.all_symbols` is the union of holdings,
benchmark and hedge instrument — the symbols the panel needs to contain.

### Changing the hedge instrument

Set `hedging.hedge_instrument` and you are done for the common case. The
new symbol is added to the panel automatically, the Hedger uses it for the
minimum-variance ratio, and the backtest measures R² against it instead of
against the benchmark.

Three things to check before you trust the result:

**The symbol has to exist in your data.** The synthetic fixture has
parameters for a fixed set of symbols in the `_PARAMS` table in
`src/data/synthetic.py`, and it silently falls back to a generic parameter
set for anything else. On a real source, a missing symbol raises.

**The hedge instrument is not the benchmark, or the R² is measuring the
wrong thing.** If you hedge with the benchmark itself, the "hedging
equation" R² is the variance of the portfolio explained by the market — a
number that can look excellent while saying nothing about whether *that
instrument* is a good hedge for *this* portfolio.

**Re-run the gates, and expect them to move.** A different hedge instrument
is a different strategy. The whole point of the four gates is that they
catch exactly this kind of change. Run `python scripts/backtest.py` and
report the new numbers, including the ones that got worse.

### Changing the risk limits

The `risk:` section maps directly onto `RiskLimits` in `src/config.py`:

```python
@dataclass(frozen=True)
class RiskLimits:
    """Hard limits. The Risk seat enforces these and nobody else may relax them."""

    max_gross_hedge_pct: float = 1.0
    risk_per_trade_pct: float = 0.02
    min_reward_to_risk: float = 1.5
    max_legs: int = 5
```

These are enforced by `RiskPolicy.evaluate` in `src/policy/risk.py`, in this
order: the kill switch, then the judge verdict, then judge agreement, then
the reward-to-risk floor, then the gross hedge cap, then the leg count, then
the cost-versus-benefit test, then the per-trade risk budget. Every veto
records the stage it happened at and the reason.

Two notes about the current validation, so you do not assume more than is
there:

- `RiskLimits` validates its own ranges in `__post_init__` and raises
  `ConfigError` for a non-positive `max_gross_hedge_pct`,
  `risk_per_trade_pct` or `min_reward_to_risk`, and for `max_legs` below 1.
  It used to have no validation of its own, so a typo like
  `risk_per_trade_pct: -0.02` loaded silently and produced a Risk seat that
  misbehaved later. **A limit that cannot be honoured should stop the
  process at load time**, not produce a plausible-looking wrong answer
  later. If you add a limit field, validate it in the same place.
- `max_legs` is not only a Risk limit. It is also the Scan seat's
  `max_candidates`, in both `src/desk.py` and `src/backtest.py`:
  `ScanPolicy(cfg.portfolio.benchmark, max_candidates=cfg.risk.max_legs)`.
  Changing it changes how many holdings are screened, not just how many legs
  may be open.

### The loud validation behaviour

`ConfigError` is defined in `src/config.py`:

```python
class ConfigError(ValueError):
    """A config file is missing something the desk cannot run without."""
```

The module docstring states the rule: *validation is deliberately loud. A
missing or misspelled key raises `ConfigError` with the key name and the
file path. Silent defaults in a risk system are a bug, not a convenience.*

What that looks like in practice:

```python
>>> DeskConfig.from_yaml("examples/holdings.example.yaml")
>>> DeskConfig.from_yaml("missing.yaml")
ConfigError: config file not found: missing.yaml
```

The `__post_init__` validators are where most of the loudness lives.
`HedgingParams` raises on an unknown rebalance frequency, on a lookback too
short to estimate a beta, and on a negative shrinkage constant.
`DataConfig` raises on an unknown source. `DeskConfig.from_dict` raises on a
holdings list that is not a list, on a holding with no `symbol`, and on a
`shares` value that is not a number — and those messages name the file and
the index of the offending entry:

```python
raise ConfigError(f"{where}: portfolio.holdings[{i}] is missing 'symbol'")
```

So when you add a config key, you add it in three places: the dataclass
field, the `from_dict` parsing, and the YAML example. And if the key has a
sensible range, validate it in `__post_init__` and raise `ConfigError` —
not a default, and not a silent clamp.

## Definition of done

A pull request is ready when all of these are true.

**Tests**

- [ ] `python -m pytest tests/ -q` passes, and it passed before your change
      too.
- [ ] Any new statistic is cross-validated against an *independent* library
      or solver, in a test. Not a re-implementation of your own code —
      against something else.
- [ ] Any new gate has tests for both the passing and the failing direction.
- [ ] Any new seat has a test, and the desk and backtest still run.

**Correctness**

- [ ] No look-ahead. Every decision uses data strictly before its date, and
      the fill is at a close the decision could not have known. If you added
      a seat, it receives the cut-off panel and does not filter by date
      itself. If you touched a caller, you checked the `fill_date` it passes
      — the broker does not check it for you.
- [ ] Every cost is charged. No path that skips the fee, the slippage or the
      spread.
- [ ] The Risk seat still holds the only veto and the only signature. Your
      change does not create an `OrderIntent`, does not bypass
      `RiskPolicy.evaluate`, and does not touch the paper broker's refusal
      of unsigned intents.
- [ ] The journal row is written before the outcome, with an
      `idempotency_key`, an `information_cutoff` and an
      `input_snapshot_hash`.
- [ ] Failures are loud. No silent default, no silent clamp, no silent
      substitution of a data source.

**Honesty**

- [ ] Every number you added to the docs is reproducible by a command in
      this repository.
- [ ] `python scripts/audit_claims.py` passes, or you have explained why
      not.
- [ ] The synthetic fixture is still described as a test fixture, and no
      claim about real markets has crept in.
- [ ] If you changed a threshold, you said where the new number comes from.
      Threshold 25% R² is Healy and Lo's; gate 2's IC floor and t-threshold
      are this repository's own choices and are presented as such.
- [ ] If you tried several variants to get a result, you said how many, and
      passed `--trials` to the backtest.

**Scope**

- [ ] One thing per pull request, and the description says what changed and
      what it does to the results.
- [ ] You did not change the method to fit the result.
